# 探索卡顿：后续优化候选

记录日期：2026-10-19。状态：待后续处理；本文记录调查结论，不表示已经实施下列优化。

当前代码基线：`baa3ad3`（复用结构生成中的共享密度函数映射）。已完成的方案和验证见 [structure-noise-setup.md](structure-noise-setup.md)。

## 已解决的部分与剩余现象

结构噪声准备已改为在一次映射中复用共享分支。同一构建、同一进程的 14 个预热目标区块中，结构生成合计从 29.131 秒降至 10.259 秒，线程分配从 10.122 GB 降至 1.759 GB。28 对结构 NBT、3,618 项高度与地形列检查一致，141 条单测通过。

这组数字是优化作用域开关的对比，基线也带有新增 mixin 的透传路径，不能直接解释为整合包 FPS 提高 65%。

后续完整客户端沿新路线 x=3072、z=0…2048 探索。进入 z=256 后的 167 个帧统计窗口中，最大单帧 741.56 ms，没有超过 1 秒的帧；探索 JFR 仍有一次渲染线程分配等待，持续 216.27 ms。仍有明显卡顿，尚不能宣布探索卡顿全部解决。

测试使用原包的 201 个模组及同一种子的存档副本，NeoForge 21.1.249。本机结果不能替代原故障机的验证。QA 副本关闭了天空时间追踪；原客户端的该配置未修改。

## 1. 客户端生物群系缓存失效

位置：

- `dimblend/src/main/java/dimblend/mixin/ClientChunkCacheMixin.java`
- `dimblend/src/main/java/dimblend/mixin/BiomeManagerMixin.java`
- `dimblend/src/main/java/dimblend/BiomeCacheHolder.java`

当前逻辑在区块到达、卸载、生物群系更新和视距变化后清空整张缓存。连续到达或卸载一批区块时，会重复执行 `ConcurrentHashMap.clear`。

最新探索采样中，渲染线程 1,270 个 Java CPU 样本有 48 个落在 `ConcurrentHashMap.clear`，约 3.8%；采样噪声为高。优化前两份采样对应约 5.8% 和 9.8%。这些是活跃 Java CPU 的采样占比，不是帧墙钟时间；路线和采样条件不同，不能用它们直接计算优化前后收益。

建议先记录缓存命中率、实际条目数、失效次数、每次清空耗时，以及同批数据包中重复清空的比例。随后比较局部失效、合并同批失效或有界缓存方案，选择实测收益更好的方案。

正确性要求：保留目前对未加载邻区块的保护，避免把缺区块时的回退群系长期缓存。局部失效必须覆盖查询所依赖的邻域；跨群系边界、区块反复加载/卸载、视距变化和维度切换均需验证。合并失效也必须保证期间不会读到已经过期的结果。

验收：命中率与失效成本改善；同一路线的帧尾延迟降低；群系、天空和边界显示与原路径一致。

## 2. 剩余的大型结构高度查询

优化后的预热样本中，部分主世界结构任务仍需要约 1.6–2.9 秒，单任务线程分配约 200–410 MB。共享分支映射已减少浪费，但剩余成本仍值得处理。

建议增加每个结构任务的查询统计：请求的 x/z、生成器、随机状态、垂直范围、高度图类型、重复次数，以及列准备和高度扫描的各自成本。先证明存在可观的重复查询，再加入缓存。

若命中率足够，可考虑只存活于单次结构生成任务的有界高度结果缓存。键必须包含所有影响结果的输入，不能仅用 x/z。不要跨列或跨工作线程共享带可变插值状态的 `NoiseChunk`。

同时按结构 ID/模板归因，区分首次模板读取、数据修复、JIT 预热和稳定运行的地形查询成本。现有数据不足以把首次长停顿归因于某一个第三方结构模组，也不证明所有首次加载问题已解决。

验收：同种子、相同生成条件下完整结构 NBT 和必要的地形列结果一致；分别报告冷启动与预热计时、线程分配、缓存命中率和上限。轻量特殊纬度样本也应复核，避免为低成本查询增加更大的维护成本。

## 3. 生物群系搜索与渲染中的临时分配

最新 JFR 的分配样本仍出现：

- Biolith 的 `Climate$RTree.biolith$searchTreeGet`、`SimpleArrayIterator` 及相关数组。
- Iris 批量实体渲染的 `SegmentedBufferBuilder` 相关 lambda。
- 列表迭代器、临时数组和部分向量对象。

这些是待定位的分配热点，不能据此断定 Iris、Biolith 或显卡是卡顿根因。分配采样的权重是估计值，不能当作精确分配字节或常驻堆大小。

建议按线程、场景和完整调用链归因。群系搜索重点核对同一列/群系采样点是否被重复查询；渲染重点核对列表遍历、批次提交和临时闭包的创建频率。只有输入、生命周期和线程边界明确后才复用对象或查询结果。

验收：在相同视角、区块与模组设置下对照 CPU、分配速率、分配等待和帧尾延迟；验证群系结果与渲染画面一致。CPU/JFR 证据不能替代 GPU 时间测量。

## 4. 模拟线程同步等待区块

优化前捕获到的调用链包含：

`Create RotationPropagator / Simulated 额外动力邻居查询 -> Level.getBlockState -> ServerChunkCache.getChunk -> managedBlock`。

它说明动力网络查询可能同步等待区块，而不只是在已加载数据中查找。渲染帧率正常时，模拟仍可能因等待而停顿。不过，现有证据没有量化该路径在最新构建中的占比。

建议使用实际列车/动力网络场景，并在探索加载边界附近重新采样，记录查询坐标、区块状态、等待时间和触发者。确认后再评估把扫描安排到所需区块可用之后，优先使用现有动力网络的重试或生命周期机制。

不能简单把未加载邻居当成空气，或无后续重试地跳过传播；这可能改变轴网连接、动力源和车辆状态。验收需包含区块加载/卸载后网络恢复、拓扑与动力结果正确，以及模拟等待时间下降。

## 后续验证的共同约束

- 每次只改一个候选，保留同种子与相同初始区块状态的基线，分别比较预热和冷启动。
- 分别观察渲染、模拟、世界生成工作线程，以及分配等待；平均 FPS 不能覆盖所有停顿。
- 大型结构对照应比较结构 NBT 与必要的方块结果。新增或调整 mixin 后必须在完整客户端实际走到目标路径。
- 不把调试工具的停顿算作游戏瓶颈：本次 `jcmd Thread.print -l` 曾造成约 9–13 秒 safepoint；常规观察避免这类锁枚举。记录器启动、截图和传送也要在时间线上标记。
- JFR 分类脚本会因录制起点的模块清单事件误判为启动阶段；应结合实际坐标、游戏事件与截图判定阶段。
- 本次没有证据证明存在内存泄漏。增加堆上限只能作为受控诊断对照，不能代替减少无效工作。
